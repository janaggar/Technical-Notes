Question 1 — Theory: sequential vs parallel, threads, concurrency

a) Sequential Algorithms

A sequential algorithm executes one operation at a time on a single processor. The steps are strictly ordered, so each instruction must finish before the next one begins. There is no overlap of work — total time is simply the sum of the individual step costs.

b) Parallel Algorithms & Efficiency

A parallel algorithm splits the work across multiple processors or cores that run simultaneously, so several operations execute at the same instant. The goal is to reduce wall-clock time by doing independent pieces of work concurrently.

Efficiency measures how well the processors are actually used:

E = Speedup / p = T1 / (p · Tp)

where T1 is the sequential time, Tp the time on p processors. It is a value between 0 and 1 giving the fraction of the total processor power that is usefully employed (1 = perfect, ideal speedup).

c) Measuring running time

The standard approach is asymptotic analysis: count the number of basic operations as a function of the input size n and express it with big-O notation (O(·)), distinguishing worst-case, average-case, and best-case. Alternatively one can measure empirically by timing the program on real inputs, but asymptotic analysis is machine-independent and preferred.

d) Thread and multithreading

A thread is the lightest unit of execution within a process: it has its own stack, registers, and program counter, but shares the process's memory (code, heap, globals) with the other threads. Multithreading means having multiple threads inside one process running concurrently, allowing the program to do several things at once while sharing data cheaply.

e) Thread vs process

A process is an independent program in execution with its own private address space; it is isolated from other processes. A thread lives inside a process and shares that process's memory with its sibling threads. Consequently threads are much cheaper to create and to communicate between (shared memory), whereas a process is heavier and isolated.

f) Concurrency vs parallelism

Concurrency is dealing with many tasks by interleaving them — they make progress by being time-sliced, which can happen even on a single core; it is about the structure of the program. Parallelism is actually executing many tasks at the very same instant on multiple cores; it is about execution. You can have concurrency without parallelism, but parallelism requires multiple processing units.

Question 2 — Threads: stacks, sharing, saturation, mapping

a) Separate stacks?

Yes. Each thread runs its own sequence of function calls, so it needs its own private call stack to hold its local variables, return addresses, and parameters. Sharing one stack would corrupt every thread's call chain.

b) Separate copies of the executable?

No. All threads of a process share the single code image (the text segment) loaded once into the process's address space. Only the per-thread state (stack, registers, PC) is private.

c) Concurrency without parallelism?

Yes. On a single core, the scheduler time-slices among threads, rapidly switching between them so they all make progress in an interleaved fashion. This gives concurrency (overlapping logical progress) without parallelism (no two instructions run at the same physical instant).

d) When does increasing M raise saturation throughput?

Only when the worker threads spend time blocked — for example waiting on I/O, disk, or the network. Extra threads can then run on the cores that would otherwise sit idle during those stalls, keeping the CPUs busy. If the workload is already CPU-bound with about M ≈ N busy threads, adding more threads only adds context-switch and contention overhead and gives no throughput gain.

e) Maximum threads in parallel?

2. Parallelism is bounded by the number of kernel threads, because the kernel only schedules those onto cores. With just 2 kernel threads, at most 2 user threads can run at the same instant — independent of the 10 user threads or the 8 cores available.

Question 3 (5 pts)
How to make Merge Sort Concurrent? (Hint: sort the two halves concurrently.)

Question 3 — Concurrent Merge Sort

Merge sort already splits the array recursively into two halves, sorts each half, then merges the two sorted halves. The two recursive sorts are completely independent — neither reads the other's data — so they can be done in parallel instead of one after the other.

The idea: at each recursive level, fork a separate thread/task to sort the left half while the current thread sorts the right half, then join (wait for both) and perform the sequential merge. To avoid the overhead of creating threads for tiny subarrays, switch to a plain sequential sort below a small cutoff size.

The total work stays O(n log n) (the same number of comparisons), but the parallel span/depth drops to O(n) when the merge is sequential (the merge of the top level alone costs O(n)). If the merge step is also parallelized, the span improves to O(log2n).

Suggested pseudocode solution

parallelMergeSort(A, lo, hi):
    if hi - lo <= CUTOFF:
        sequentialSort(A, lo, hi)        // small subarray
        return
    mid = (lo + hi) / 2
    fork  parallelMergeSort(A, lo, mid)  // sort left half in a new task
    do    parallelMergeSort(A, mid, hi)  // sort right half here
    join                                 // wait for the left task
    merge(A, lo, mid, hi)                // combine the two sorted halves
Question 4 (5 pts)
There are n people, each of whom knows one unique scandal that nobody else knows. Whenever two of them call each other, they exchange ALL the scandals they currently know. What is the minimum number of calls needed so that everyone knows all scandals?

Question 4 — The Gossip Problem

This is the classic gossip (telephone) problem. For n ≥ 4 the minimum number of calls is:

2n − 4 calls

Strategy. Choose 4 "core" people. The work is done in three phases:

  • Gather in (n−4 calls): each of the other n−4 outsiders calls a core person, dumping their scandal into the core group.
  • Core exchange (4 calls): the 4 core people gossip among themselves (e.g., two pairs swap, then the partners swap) so that all 4 end up knowing every scandal.
  • Spread out (n−4 calls): each of the n−4 outsiders is called back by a core person and receives the complete set.

Total = (n−4) + 4 + (n−4) = 2n − 4.

Small cases: n=1 → 0, n=2 → 1, n=3 → 3, n=4 → 4.

Lower-bound intuition: every outsider must take part in at least two calls — one to send their scandal into the group and one to receive everything back — which forces roughly 2n calls, and the 2n−4 schedule meets this bound.

Suggested pseudocode solution

gossip(people[1..n]):                    // assume n >= 4
    core = {p1, p2, p3, p4}
    others = {p5, ..., pn}

    for each x in others:                // phase 1: gather in (n-4 calls)
        call(x, p1)                       // x dumps its scandal into core

    call(p1, p2); call(p3, p4)           // phase 2: core exchange (4 calls)
    call(p1, p3); call(p2, p4)           // now all 4 core know everything

    for each x in others:                // phase 3: spread out (n-4 calls)
        call(p1, x)                       // x receives the full set
    // total = (n-4) + 4 + (n-4) = 2n - 4
Question 5 (5 pts)
An array of N processors is given, where each processor holds a number from the array A[n] (N = n). Write a parallel algorithm to search for a value x. Give the time complexity, speedup, and efficiency.

Question 5 — Parallel Search on N Processors

Idea. Broadcast the search key x to all N processors. Each processor i compares its own element A[i] with x in O(1), all at the same time, and sets a found flag if it matches. Finally combine all the flags with an OR to learn whether any processor found x.

Complexity. The local comparison is O(1). The combine step depends on the model: on a CRCW PRAM the OR can be done in O(1) (many processors write to one location simultaneously), giving total O(1) time; on an EREW PRAM or a tree reduction the OR takes O(log n), giving total O(log n).

Speedup & efficiency. Sequential search is O(n). So speedup is O(n) (or n/log n for the tree combine), and efficiency = Speedup/p. With the O(1) result and p = n processors, efficiency is O(1/n) — very low, because most processors do one comparison then sit idle. This is the classic time-vs-work trade-off: extremely fast but not work-efficient.

Suggested pseudocode solution

parallelSearch(A[0..n-1], x):
    broadcast x to all processors
    for each processor i in parallel:    // O(1)
        flag[i] = (A[i] == x)            // true only if this cell matches
    found = OR(flag[0..n-1])             // O(1) CRCW  /  O(log n) tree
    return found

For the recurrence f(n) = 4 f(n/2) + 1, how many subproblems are there and what is their size? Give the complexity.

Question 6 — Recurrence f(n)=4f(n/2)+1

Writing the recurrence in the standard divide-and-conquer form T(n) = a·T(n/b) + f(n), we read off a = 4 and b = 2. So the problem is split into 4 subproblems, each of size n/2, with an O(1) combine cost.

By the Master Theorem, compare the driving term with nlogba = nlog24 = n2. Since the constant term O(1) is much smaller than n2, the recursion-tree leaves dominate (Case 1):

f(n) = Θ(n2)
Question 7 (5 pts)
Determine whether a value x is stored in one of the processors of a 4×4 mesh. The value x is entered and the answer is returned at processor P(0,0). For the mesh shown: x = 21 → yes; x = 2 → no.

Question 7 — Membership Search on a 4×4 Mesh

Idea. The query enters at P(0,0). First broadcast x to every processor: send it across the top row, then down each column. On a 4×4 mesh this takes O(4) = O(√n) steps. Each processor then compares x against its stored value in O(1) and produces a boolean. Finally OR-reduce all the booleans back to P(0,0) (up the columns and along the top row), again in O(√n) steps. P(0,0) reports "yes" if any processor matched.

For a √n × √n mesh holding n processors, the total time is O(√n).

Results for this mesh: x = 21 is held by processor P(2,2), so the answer is yes. x = 2 appears nowhere, so the answer is no.

Suggested pseudocode solution

meshSearch(x):                           // entered at P(0,0)
    // 1. broadcast  -- O(sqrt n)
    P(0,0) sends x along row 0
    each P(0,j) sends x down its column   // every P(i,j) now has x

    // 2. local compare -- O(1)
    for each P(i,j) in parallel:
        match(i,j) = ( value(i,j) == x )

    // 3. OR-reduce back to P(0,0) -- O(sqrt n)
    reduce match up the columns then along row 0 with OR
    return result at P(0,0)              // yes if any match
Question 8 (5 pts)
On a 4×4 mesh, compute the prefix sums in place in row-major order: each processor receives the sum of all original values that come before it in row-major order (plus its own). Example:

Question 8 — Prefix Sums on a 4×4 Mesh

Idea. Treat the mesh as a single sequence in row-major order (left to right, top to bottom) and replace each cell with the cumulative running total up to and including itself. For instance the first cell of row 1 becomes 15 = 11 + 4 (everything in row 0 plus its own value), and the bottom-right cell becomes 45, the grand total.

Parallel method (three phases):

  • Row prefix: compute a prefix sum independently within each row, in parallel — O(√n).
  • Column carry: take each row's total (its last element) and compute a prefix sum down the first column, so each row learns the offset (sum of all earlier rows) — O(√n).
  • Add offset: broadcast each row's incoming offset across that row and add it to every element — O(√n).

Total time on a √n × √n mesh is O(√n).

Suggested pseudocode solution

meshPrefixSums():
    // phase 1: prefix sum inside each row  (parallel over rows)
    for each row i in parallel:
        rowPrefix(i)                      // A[i][j] += A[i][j-1]
        rowTotal[i] = A[i][last]

    // phase 2: prefix sum of row totals down column 0
    offset[0] = 0
    for i = 1 to sqrt(n)-1:
        offset[i] = offset[i-1] + rowTotal[i-1]

    // phase 3: add each row's offset to all its cells
    for each row i in parallel:
        for each j in parallel:
            A[i][j] += offset[i]
Question 9 (5 pts)
A d-dimensional hypercube has 2d nodes. Write a procedure to broadcast an element in a 2-dimensional hypercube.

Question 9 — Hypercube Broadcast

Idea. A hypercube broadcast proceeds dimension by dimension. The source first sends the element to its neighbour along dimension 0 (the node differing in bit 0); then in the next round every informed node sends along dimension 1; and so on. Because the number of nodes that know the value doubles each round, after d rounds all 2d nodes have it. This costs O(d) = O(log P) steps.

2-D hypercube (4 nodes 00, 01, 10, 11):

  • Step 1 (bit 0): node 00 sends to 01.
  • Step 2 (bit 1): 00 → 10 and 01 → 11 in parallel.

Done in 2 steps, all 4 nodes informed.

Suggested pseudocode solution

hypercubeBroadcast(source, d):
    informed = { source }
    for k = 0 to d-1:                     // one round per dimension
        for each node u in informed in parallel:
            v = u XOR (1 << k)            // neighbour differing in bit k
            send element from u to v
            add v to informed
    // after d rounds all 2^d nodes have the element
Question 10 (5 pts)
Write a parallel algorithm for 2 processors that merges two sorted arrays A and B into a single sorted array C. Give the complexity and the efficiency.

Question 10 — Two-Processor Merge

Idea. The two arrays together hold 2n elements. Find the median of the combined set, which splits the merge into a lower half and an upper half of equal size that do not overlap. Processor 1 merges the elements below the median into the front part of C, while processor 2 merges the elements above the median into the back part of C. Because the two output regions of C are disjoint and the input ranges are determined in advance, the processors never coordinate during the merge.

Complexity. Finding the split point via the two-array median is O(log n) (binary search across both arrays). Each processor then merges at most n elements in O(n). So the parallel time is

T2(n) = O(n/2 + log n) ≈ O(n/2)

Speedup & efficiency. The sequential merge is O(n), so speedup ≈ 2× over the sequential algorithm. Efficiency = Speedup / 2 ≈ near 1 for large n, since the only overhead is the O(log n) median computation, which is negligible compared with the O(n) merge work.

Suggested pseudocode solution

parallelMerge2(A[0..n-1], B[0..n-1], C[0..2n-1]):
    // find the split: how many of the smallest n elements come from A vs B
    (ia, ib) = twoArrayMedianSplit(A, B)  // O(log n)

    // processor 1: merge the lower half into C[0 .. n-1]
    P1: merge A[0..ia-1] with B[0..ib-1]  -> C[0 .. n-1]

    // processor 2: merge the upper half into C[n .. 2n-1]
    P2: merge A[ia..n-1] with B[ib..n-1]  -> C[n .. 2n-1]

    // both write disjoint regions of C, no synchronization needed

Question 1 — Concurrency theory and deadlock

a) Primary goal of concurrent programming

The primary goal is to structure a program as multiple tasks that make progress together, so the program is more responsive, achieves higher throughput, and makes better utilization of multi-core hardware — all while correctly coordinating access to shared state so results stay consistent.

Goal: organize work as cooperating tasks for responsiveness, throughput and full use of available cores, with correct synchronization of shared data.

b) Parallel algorithms and efficiency

↺ Repeated — also answered in Final 2022/23 · Q1(b).

A parallel algorithm is one designed so that several operations run at the same time on multiple processing units. The work is split into subtasks that execute simultaneously and whose partial results are combined into the final answer.

Efficiency measures how well the processors are used. With sequential time T1 and parallel time Tp on p processors:

Speedup S = T1 / Tp  ·  Efficiency E = T1 / (p · Tp) = S / p. E = 1 (100%) is ideal/linear; real values are lower due to overhead and the sequential fraction.

c) Thread and multithreading

↺ Repeated — also answered in Final 2022/23 · Q1(d).

A thread is the smallest unit of execution scheduled by the OS: a single sequential flow of control with its own program counter, registers and stack, but sharing the code, heap and open files of its process. Multithreading is running several threads within one process concurrently, letting them share memory while making independent progress (and running truly in parallel on multiple cores).

d) Thread vs process

↺ Repeated — also answered in Final 2022/23 · Q1(e).

  • A process has its own private address space; threads of the same process share the address space (heap, globals, files).
  • A process is heavier to create and switch; a thread is lightweight, since less state must be saved/restored.
  • Inter-process communication needs OS mechanisms (pipes, shared memory); threads communicate directly through shared variables, which is fast but needs synchronization.
  • A crash in one process is isolated; a misbehaving thread can corrupt the whole process.

e) Concurrency vs parallelism

↺ Repeated — also answered in Final 2022/23 · Q1(f).

Concurrency is about dealing with many tasks at once: structuring a program so multiple tasks are in progress and interleaved — possible even on a single core via time-slicing. Parallelism is about doing many tasks at the same instant on multiple cores. Concurrency is a design/structuring concept; parallelism is a hardware execution concept. Code can be concurrent without being parallel, and parallel execution is one way to run concurrent tasks.

f) The four deadlock conditions and a prevention strategy

All four Coffman conditions must hold simultaneously for a deadlock:

  • Mutual Exclusion — at least one resource is held in a non-shareable mode.
  • Hold and Wait — a process holds a resource while waiting to acquire others.
  • No Preemption — resources cannot be forcibly taken; they are released only voluntarily.
  • Circular Wait — a cycle of processes exists, each waiting for a resource held by the next.

Prevention strategy: break one of the four conditions. The most practical for shared resources is to impose a global lock ordering — every process must acquire resources in the same fixed total order. This makes a circular wait impossible, so deadlock cannot form. Alternatives: request all resources at once (breaks hold-and-wait), allow preemption of held resources, or use the Banker's algorithm for deadlock avoidance (grant a request only if a safe state remains).

Four conditions: Mutual Exclusion, Hold-and-Wait, No Preemption, Circular Wait. Prevent most simply by enforcing a single global resource-ordering (eliminates circular wait).
Question 2 (10 pts)

Question 2 — Short concurrency explanations

a) Separate stacks for threads

↺ Repeated — also answered in Final 2022/23 · Q2(a).

Yes — each thread executes its own independent call chain, so it needs its own stack to hold its local variables, parameters, return addresses and saved registers. A single shared stack would corrupt these frames as threads call functions at different times. Separate stacks keep each thread's control flow private and correct.

b) Concurrency without parallelism

↺ Repeated — also answered in Final 2022/23 · Q2(c).

Yes. On a single core the scheduler can interleave several tasks by time-slicing, so multiple tasks are in progress at once (concurrent) even though only one instruction executes at any instant (not parallel). Concurrency is a structuring property; parallelism requires multiple cores.

c) When raising M increases saturation throughput

↺ Repeated — also answered in Final 2022/23 · Q2(d).

Only when worker threads block on I/O (disk, database, network). Extra threads then fill the gaps left by blocked ones, keeping the N cores busy and raising throughput. Once the workload is purely CPU-bound, the cores are already saturated at M ≈ N, so adding more threads gives no gain and can even hurt due to context-switching and contention overhead.

d) 10 user threads on 2 kernel threads, 8 cores

↺ Repeated — also answered in Final 2022/23 · Q2(e).

At most 2 run in parallel. Only kernel threads are scheduled onto cores, and there are only 2 of them, so the 8 cores and 10 user threads cannot raise the limit beyond the number of kernel threads.

Max parallel = min(kernel threads, cores) = min(2, 8) = 2.
Question 3 (5 pts)
Design and analyze a concurrent merge sort. Explain how you would partition the data and manage the threads.

Question 3 — Concurrent merge sort

↺ Repeated — also answered in Final 2022/23 · Q3.

Idea. Merge sort recursively splits the array in half until single elements remain, then merges sorted halves back up. The two halves are independent, so they can be sorted at the same time. We exploit this with a fork-join pattern: fork one task per half, sort them concurrently, join (wait for both), then merge the results.

Partitioning & thread management. Split each subarray at the midpoint. Use a thread pool (or fork-join framework) rather than spawning a raw thread per call, to bound the number of live threads and avoid creation overhead. Apply a sequential cutoff: below a small size threshold, sort in-place sequentially so tiny tasks do not waste scheduling overhead. The merge step is sequential per node.

Analysis. Total work is O(n log n) (same as sequential). The critical-path span is O(n), dominated by the final sequential merge of size n, giving best-case parallelism of O(log n). (A parallel merge would lower the span to O(log2 n).)

Suggested pseudocode solution

function parMergeSort(A, lo, hi):
    if hi - lo <= CUTOFF:
        sequentialSort(A, lo, hi)         // small chunk
        return
    mid = (lo + hi) / 2
    left  = fork parMergeSort(A, lo, mid)   // run concurrently
           parMergeSort(A, mid, hi)
    join left                              // wait for forked half
    merge(A, lo, mid, hi)                  // sequential merge

function merge(A, lo, mid, hi):
    copy A[lo..hi] into temp
    i = lo; j = mid; k = lo
    while i < mid and j < hi:
        A[k++] = (temp[i] <= temp[j]) ? temp[i++] : temp[j++]
    copy any remainder of temp back into A
Question 4 (5 pts)
A server-clients system is simulated. Each minute exactly ONE of 5 clients generates a task. The client that generates the task follows a geometric ("exponential") law: P(client 3) = 2·P(client 4), P(client 4) = 2·P(client 5), … — i.e. the weight of client i is proportional to 2−i (each earlier client is twice as likely as the next). A distributor then assigns each generated task to one of 4 servers chosen UNIFORMLY at random. Write TWO codes simulating the generation and the distribution.

Question 4 — Client generation and task distribution

Generation. Give each client i a weight wi = 2(K−i) so that each earlier client is twice as likely as the next (e.g. for 5 clients use exponents 4,3,2,1,0 → weights 16,8,4,2,1). Normalize by the total weight to get probabilities pi, then sample by inverse-CDF: draw u ∈ [0,1), walk the cumulative probabilities, and pick the first client whose cumulative sum ≥ u. This reproduces the required geometric "twice as likely" law.

Distribution. The distributor picks a server uniformly: server = 1 + floor(uniform() · 4), so each of the 4 servers has probability 1/4 independently of which client produced the task.

Suggested pseudocode solution

// ---- generation: pick which of N clients produces the task ----
function generateTask(N):                 // N = 5
    weights = []
    for i in 1..N:
        weights[i] = 2 ^ (N - i)          // 16,8,4,2,1  (cli1 most likely)
    total = sum(weights)
    u = uniform() * total                 // u in [0, total)
    cum = 0
    for i in 1..N:
        cum = cum + weights[i]
        if u < cum:
            return client i               // first client whose cumulative >= u

// ---- distribution: assign the task to one of 4 servers uniformly ----
function distributeTask(task, S):         // S = 4
    server = 1 + floor(uniform() * S)     // each server prob = 1/S
    sendTo(server, task)
    return server
Question 5 (5 pts)
  1. Give an O(log n)-time SEQUENTIAL algorithm to find the median of all 2n elements of two sorted arrays A and B, each of size n. Provide pseudocode and prove the running time.

Question 5 — Median of two sorted arrays; recurrence shape

a) O(log n) median of two sorted arrays

Idea. Compare the medians of the two arrays. If median(A) < median(B), the overall median of all 2n elements cannot lie in A's lower half nor in B's upper half, so those halves are discarded and we recurse on the remaining halves (keeping the discarded counts equal so the median position is preserved). Symmetrically if median(A) > median(B). Each step halves the candidate size, so we converge quickly.

Proof of running time. Each recursive call discards half of each remaining subarray and does O(1) comparison work, giving T(n) = T(n/2) + O(1). By the Master Theorem (or by unrolling: O(1) work for log n levels), T(n) = O(log n).

Suggested pseudocode solution

function median2(A, B):                    // both sorted, equal length
    while length(A) > 2:
        ma = median(A);  mb = median(B)
        k  = floor(length(A) / 2)          // discard k from each side
        if ma == mb: return ma
        if ma < mb:
            A = A[k .. end]                 // drop A's lower half
            B = B[0 .. length(B)-k]         // drop B's upper half
        else:
            A = A[0 .. length(A)-k]         // drop A's upper half
            B = B[k .. end]                 // drop B's lower half
    // base case: 2 elements each
    return ( max(A[0], B[0]) + min(A[1], B[1]) ) / 2

b) f(n) = 4 f(n/2) + 1

↺ Repeated — also answered in Final 2022/23 · Q6.

There are 4 subproblems, each of size n/2. With a = 4, b = 2, f = O(1): nlog24 = n2 dominates, so by the Master Theorem the complexity is Θ(n2).

Question 6 (5 pts)
Design a concurrent algorithm to generate ALL permutations of the set [1..n] using multiple threads. Discuss Partitioning, Concurrency, Synchronization and Performance.

Question 6 — Concurrent permutation generation

Idea. Fix the first element of the permutation. There are n possible first elements, and each choice gives an independent group of (n−1)! permutations of the remaining items. Hand each first-element (or a range of them) to a different thread.

Partitioning. Split the n first-element choices among the p threads (e.g. thread t handles first elements t, t+p, t+2p, …). Each group is fully independent.

Concurrency. Each thread, on its own copy of the remaining set, recursively generates the (n−1)! permutations for its fixed prefixes. Because groups never share the same first element, no two threads ever produce the same permutation and there are no read/write conflicts on shared data.

Synchronization. Each thread writes into its own output buffer, so almost no locking is needed. Results are combined at the end by concatenation, or streamed into a single concurrent queue if a unified output is required.

Performance. Total work is O(n · n!) (n! permutations, O(n) to emit each). With p ≤ n balanced threads, speedup ≈ p and efficiency = speedup/p is near 1, because the n branches are equal-sized so load is well balanced.

Suggested pseudocode solution

function permuteAll(n, p):
    parallel for t in 0 .. p-1:
        local out = []                     // private buffer per thread
        for first in (t+1) .. n step p:    // disjoint set of first elements
            rest = [1..n] without first
            permuteRec([first], rest, out)
        emit out                           // concat, or push to concurrent queue

function permuteRec(prefix, remaining, out):
    if remaining is empty:
        out.append(prefix)
        return
    for each x in remaining:
        permuteRec(prefix + [x], remaining without x, out)
Question 7 (5 pts)
  1. You have an input file of four billion integers and only 1 GB of RAM. Generate an integer that is NOT contained in the file. Analyze the complexity.
  2. How can Dijkstra's shortest-path algorithm be parallelized?

Question 7 — Missing integer with limited RAM; parallel Dijkstra

a) Find a missing integer

Idea. 32-bit integers span 0 … 232−1 (≈ 4.29×109 distinct values). Allocate a bit vector of 232 bits = 229 bytes = 512 MB, which fits in 1 GB. Scan the file once, setting the bit for each value seen. Then scan the bitmap for the first 0-bit; its index is an integer not present in the file.

Bitmap of 232 bits (512 MB) → set bits in one pass, then report first clear bit. Time O(n), memory 512 MB.

If memory were tighter: do a two-pass bucket/counting approach. Split the integer range into buckets; in pass 1 count how many file values fall into each bucket; a bucket whose count is below its capacity must contain a missing value. In pass 2, recurse into just that bucket (now using a small bitmap). This trades extra passes for far less memory.

b) Parallelizing Dijkstra

Dijkstra is inherently sequential because each step selects the single global-minimum-distance unsettled vertex, creating a dependency chain. Parallelism is therefore limited to:

  • Parallel edge relaxation — once the current vertex is settled, relax all of its outgoing edges (or the whole frontier) concurrently.
  • Parallel reduction for the minimum — find the next min-distance vertex with a parallel reduction over the distance array.
  • Approximate / bucketed priority queues — algorithms like Δ-stepping process a whole bucket of "light"-edge vertices in parallel, relaxing the strict global-min ordering to expose much more parallelism.

Suggested pseudocode solution

parallelDijkstra(G, s):
    dist[] = INF; dist[s] = 0
    while unsettled vertices remain:
        u = parallelReduceMin(dist over unsettled)   // parallel min
        mark u settled
        parallel for each edge (u, v, w):            // relax in parallel
            atomic: dist[v] = min(dist[v], dist[u] + w)
    return dist
Question 8 (5 pts)
Parallel matrix multiplication of A (n×m) × B (m×p) = C (n×p).
  1. What steps are required to parallelize it?
  2. How would you distribute the work in a SHARED-memory versus a DISTRIBUTED-memory environment?

Question 8 — Parallel matrix multiplication

Idea. Every output cell C[i][j] = Σk A[i][k]·B[k][j] is computed independently of all others. So we assign disjoint sets of output cells (rows or blocks) to different processors and let each compute its own dot products — there are no write conflicts.

a) Steps to parallelize

  • Partition the output C among the p workers (by rows, columns or 2-D blocks).
  • Each worker reads the rows of A and columns of B it needs.
  • Each worker computes the dot products for its assigned block of C.
  • Each worker writes its disjoint part of C — no synchronization on writes is required.

b) Shared-memory vs distributed-memory

Shared-memory (e.g. OpenMP). All threads see A, B and C in one address space, so it is enough to parallelize the outer loop(s) over rows/blocks of C. No explicit data movement is needed, but you must watch cache locality and false sharing (block the loops, keep each thread's output region separate).

Distributed-memory (e.g. MPI). The matrices are split across nodes, so a node does not automatically hold the rows/columns it needs. You must explicitly send the required rows of A and columns of B (or use block algorithms like Cannon's or SUMMA) and then gather the partial results. Here communication cost typically becomes the bottleneck, so the goal is to minimize and overlap messages.

Suggested pseudocode solution (shared-memory)

parallelMatMul(A, B, C, n, m, p):
    parallel for i in 0 .. n-1:            // rows of C split across threads
        for j in 0 .. p-1:
            sum = 0
            for k in 0 .. m-1:
                sum += A[i][k] * B[k][j]
            C[i][j] = sum                  // disjoint write, no lock needed

d) Prefix-sums (scan)

Definition. Given a sequence a0, a1, …, an−1, the (inclusive) prefix-sums problem computes S[i] = a0 + a1 + … + ai for every i — each output is the running total up to that position.

Algorithms and complexity.

  • Sequential: one left-to-right pass, O(n) work.
  • Hillis-Steele (naïve parallel scan): O(log n) time but O(n log n) total work.
  • Blelloch (work-efficient, up-sweep + down-sweep over a tree): O(log n) time and only O(n) work.

Uses. stream compaction (filtering with parallel index assignment), radix sort, computing cumulative counts/histograms, line-of-sight and other running-aggregate problems.

Time-vs-operations trade-off. Reducing the parallel depth (time) toward O(1) generally forces more total operations (work) — Hillis-Steele is shallow but does O(n log n) work, while Blelloch keeps O(n) work at the same depth. You balance parallel time (depth) against total work to fit the available processors.

Question 10 (5 pts)
  1. A parallel algorithm runs in 5 s on 4 processors and 20 s on 1 processor. Compute the speedup and efficiency and state the implications.

Question 10 — Speedup/efficiency; CPU vs GPU strategy

a) Speedup and efficiency

Speedup S = T1 / Tp = 20 / 5 = 4. Efficiency E = S / p = 4 / 4 = 1 = 100%.

S = 4, E = 100% — ideal/linear scaling: every core is fully utilized.

Implications. This is perfect linear speedup, which is rare in practice. By Amdahl's law any sequential fraction plus communication/synchronization overhead normally caps efficiency below 1; achieving E = 1 implies a near-fully-parallelizable workload with negligible overhead.

b) CPU (n=20, k=10, 4 cores) vs GPU strategy

CPU strategy. Divide the work into about 4 balanced coarse-grained chunks (one per core) and run them on a thread pool with work-stealing to keep all cores busy if some chunks finish early. Keep tasks coarse enough to amortize thread-creation and synchronization overhead, and avoid oversubscription (don't spawn far more threads than cores).

GPU strategy. The opposite granularity: launch thousands of lightweight SIMT threads for fine-grained data parallelism. Optimize for coalesced memory access, minimal branch divergence within a warp, and minimal host↔device transfers. A GPU favors massive fine-grained parallelism, whereas the 4-core CPU favors a few heavy, coarse tasks.

Q1 — Merging two sorted arrays

(a) O(n) sequential merge

Keep two pointers, one at the front of A and one at the front of B. Repeatedly compare the two front elements, copy the smaller one into C, and advance that pointer. When one array is exhausted, copy the remaining tail of the other. Every comparison consumes exactly one element, so after 2n copies C is fully sorted. Each element is touched once, giving linear time and no comparisons wasted.

Time O(n), extra space O(n) for C.

Suggested pseudocode solution

MERGE(A, B, n):
    i = 0; j = 0; k = 0
    while i < n and j < n:
        if A[i] <= B[j]:
            C[k++] = A[i++]
        else:
            C[k++] = B[j++]
    while i < n: C[k++] = A[i++]
    while j < n: C[k++] = B[j++]
    return C

(b) Median of all 2n elements in O(log n)

↺ Repeated — full answer in Final 2024/25 · Q5(a).

Compare the median of A with the median of B. The half that cannot contain the overall median is discarded from each array, halving the search every step. This yields T(n) = T(n/2) + O(1) = O(log n).

(c) Two-processor parallel merge

↺ Repeated — full answer in Final 2022/23 · Q10.

Use a median/rank split so the combined output is divided in two; each processor merges at most n elements into its own disjoint region of C with no conflicts. Cost is the rank computation plus a half-size merge: O(n/2 + log n).

(d) Generalization to P processors and work-optimality

Choose P−1 splitter values by repeated median/rank queries so that the merged output is cut into P contiguous blocks of about 2n/P elements each. Processor i locates the matching ranges in A and B (via binary search, O(log n)) and merges its slice into a disjoint region of C, so all P processors run in parallel with no overlap. The per-processor merge dominates: TP(n) = O(n/P + log n). Total work is O(n) merge work plus O(P log n) splitter work.

TP(n) = O(n/P + log n); work = O(n + P log n), which stays O(n) (work-optimal) as long as P = O(n / log n).

Q2 — Prefix sums (scan)

↺ Repeated — full answer in Final 2024/25 · Q9(d).

Definition. Given an array x0, …, xn−1 and an associative operator (e.g. +), the scan produces all prefixes: the inclusive scan outputs si = x0 + … + xi, and the exclusive scan outputs the sum of all elements strictly before i.

Parallel algorithms. Blelloch (work-efficient) does an up-sweep (reduction tree) then a down-sweep, giving depth O(log n) and work O(n). Hillis–Steele adds elements at stride 1, 2, 4, …, also depth O(log n) but work O(n log n).

  • Uses: compaction/stream-compaction, radix sort, line-of-sight, histogram offsets, parallel allocation of buffer indices.
  • Variations: inclusive vs exclusive scan; segmented scan (independent scans within flagged segments); scans over any associative operator (max, min, ×).

Trade-off. Hillis–Steele has shorter constant factors and simpler indexing but does Θ(n log n) work (more total operations); Blelloch keeps work at Θ(n) (asymptotically optimal) at the cost of two passes and trickier indexing. Both have depth Θ(log n).

Blelloch: depth O(log n), work O(n). Hillis–Steele: depth O(log n), work O(n log n).

Q3 — Search in a rotated sorted array

Use a modified binary search. At every step compute mid; one of the two halves [lo..mid] or [mid..hi] is always fully sorted (its endpoints are in order). Check whether the target falls inside that sorted half's value range: if so, recurse there; otherwise recurse into the other half. The search space halves each iteration, so the cost is logarithmic and only O(1) extra space is used.

Worked example. Find 5 in [15, 16, 19, 20, 25, 1, 3, 4, 5, 7, 10, 14].

Iterlohimidarr[mid]ReasoningAction
101151Right half [1..14] is sorted and 5 ∈ [1, 14]lo = 6
261185arr[8] == targetreturn 8
Returns index 8. Time O(log n), space O(1).

Suggested pseudocode solution

SEARCH_ROTATED(arr, target):
    lo = 0; hi = n - 1
    while lo <= hi:
        mid = (lo + hi) / 2
        if arr[mid] == target: return mid
        if arr[lo] <= arr[mid]:            # left half sorted
            if arr[lo] <= target < arr[mid]: hi = mid - 1
            else: lo = mid + 1
        else:                              # right half sorted
            if arr[mid] < target <= arr[hi]: lo = mid + 1
            else: hi = mid - 1
    return -1

HELPER(n, lo, hi):
    if lo > hi: return hi          # floor(sqrt(n))
    mid = (lo + hi) / 2
    sq = mid * mid
    if sq == n: return mid
    if sq < n:  return HELPER(n, mid + 1, hi)
    else:       return HELPER(n, lo, mid - 1)

(m) Concurrent maximum of an array

Split the array into p chunks. Each thread scans its chunk to find a local maximum in O(n/p), then the p local maxima are combined by a tree reduction in O(log p). Total parallel time is O(n/p + log p), so the speedup is close to p when n ≫ p.

Tp = O(n/p + log p), speedup ≈ p.

Suggested pseudocode solution

PARALLEL_MAX(A, n, p):
    parallel for t in 0..p-1:
        local[t] = max of A[t*n/p .. (t+1)*n/p - 1]
    # tree reduction over the p local maxima
    for d = 1; d < p; d *= 2:
        parallel for t = 0; t < p; t += 2*d:
            if t + d < p:
                local[t] = max(local[t], local[t+d])
    return local[0]

(n) Concurrent vs sequential quicksort for large data

Sequential quicksort runs on one core with average O(n log n) / worst O(n2), uses only O(log n) stack, has negligible overhead, and is best on small-to-medium inputs. Concurrent quicksort sorts the two partitions on separate threads/tasks, performs the same O(n log n) total work but reduces the critical path to about O(log n) depth, consumes more memory for task stacks, and delivers roughly 2–8× wall-clock speedup on 4–8 cores for large data. Its task/thread overhead can dominate on small arrays, so a sequential cutoff (switch to plain quicksort below a threshold) is used.

(o) Deadlock conditions + example + fix

↺ Repeated — full answer in Final 2024/25 · Q1(f).

The four Coffman conditions are mutual exclusion, hold-and-wait, no preemption, and circular wait. Example: thread 1 locks A then waits for B while thread 2 locks B then waits for A. Fix with a global lock ordering so both acquire A before B.

(p) Detect and recover from deadlock

Build a wait-for / resource-allocation graph where processes and resources are nodes, with allocation edges (resource → process) and request edges (process → resource). A cycle in this graph indicates deadlock. Recover by terminating or rolling back a victim process inside the cycle, or by preempting and reassigning its resources, then re-running the detection.

Suggested pseudocode solution

DETECT_DEADLOCK(graph):
    for each node v:
        if DFS_HAS_CYCLE(v, visited, onStack):
            return CYCLE_FOUND        # deadlock
    return NO_DEADLOCK

# recovery: choose victim in cycle, abort/rollback, free its resources

(q) Livelock vs deadlock

In deadlock the processes are blocked and idle, stuck in a circular wait, consuming no CPU. In livelock the processes keep changing state and stay CPU-active but make no forward progress — for example two people repeatedly stepping side-to-side in a hallway, or threads that retry-and-back-off in perfect lockstep. The fix is to break the symmetry with randomized back-off or priorities so that one party proceeds.

Suggested Final Exam Problems

1. Concurrency vs parallelism

(see Final 2022/23 · Q1(f)) Concurrency is structuring a program as independently progressing tasks (interleaved on one or more cores); parallelism is actually executing multiple tasks simultaneously on multiple cores.

2. Advantages and challenges of parallel computing

Advantages: higher throughput, reduced wall-clock time, and the ability to solve larger problems by using many cores. Challenges: synchronization and race conditions, communication/overhead costs, load imbalance, and the limited speedup imposed by the sequential fraction (Amdahl).

3. Deadlock + four conditions

(see Final 2024/25 · Q1(f)) Deadlock is a circular wait where each process holds a resource the next needs. The four necessary Coffman conditions are mutual exclusion, hold-and-wait, no preemption, and circular wait.

4. Readers–Writers problem + solutions

Many readers may share data but a writer needs exclusive access. Solutions include reader-priority (writers may starve), writer-priority (readers may starve), and a fair queued version; all are built with semaphores/mutexes and a reader counter guarded by a lock.

5. Shared-memory vs distributed-memory

In shared-memory systems all processors read and write a common address space, so communication is implicit through memory but requires locks and cache coherence. In distributed-memory systems each node has private memory and processors cooperate by passing explicit messages, which scales further but adds communication latency.

6. Thread creation and synchronization

Threads are spawned (e.g. via a thread library or pool) to run functions concurrently within a shared address space. They are synchronized with locks/mutexes (mutual exclusion), semaphores (counting access), barriers (wait for all to reach a point), and condition variables (wait/signal on a predicate).

7. Thread starvation

Starvation is when a thread is perpetually denied a resource or CPU time because others keep being favored (e.g. unfair scheduling or writer-priority locks). It occurs when scheduling/lock policies lack fairness, so a low-priority or unlucky thread never makes progress.

8. Speedup

Speedup is S = T1 / Tp, the ratio of single-processor runtime to p-processor runtime. Ideal (linear) speedup is S = p, rarely reached due to overhead and the sequential fraction.

9. Amdahl's Law

With sequential fraction s and parallelizable fraction (1−s), the maximum speedup is Smax = 1 / (s + (1−s)/p). Its significance: even infinite processors cap speedup at 1/s, so the serial part limits scaling.

10. 20% sequential program — max speedup

With s = 0.20 and p → ∞, Smax = 1 / (0.20 + 0.80/p) → 1 / 0.20 = 5.

Maximum speedup = 5×.

11. Task vs data parallelism

Task parallelism runs different operations concurrently on (possibly) the same or different data, e.g. a pipeline where one thread decodes and another renders. Data parallelism applies the same operation to many data elements at once, e.g. adding two large vectors element-wise across threads.

12. SIMD vs MIMD

SIMD has one instruction stream applied to many data lanes in lockstep (vector units, GPUs). MIMD has multiple independent instruction streams over multiple data streams (multicore CPUs, clusters), allowing each core to run different code.

13. Parallel max

(see Part 4(m)) Split into p chunks for local maxima, then tree-reduce, for Tp = O(n/p + log p).

14. Parallel matrix multiplication

(see Final 2024/25 · Q8) Each output element C[i][j] is an independent dot product, so rows/blocks are assigned to threads; work O(n3), span O(log n) with a parallel reduction per element.

15. Parallel reduction and prefix sum

(see Final 2024/25 · Q9(d)) Both use a balanced tree of associative operations: reduction in O(log n) depth / O(n) work, and scan (Blelloch) in the same bounds.

16. Load balancing

Load balancing distributes work evenly so no processor idles while others are overloaded, which is essential for good speedup. Static balancing partitions work up front (good for uniform tasks); dynamic balancing assigns work at runtime, often via a shared queue or work stealing for irregular tasks.

17. Parallel merge sort

(see Final 2022/23 · Q3) Fork-join sorts the halves in parallel and merges them; work O(n log n), span O(log2n) with parallel merge.

18. Parallel odd-even transposition sort

On n elements it alternates odd and even phases; in each phase all adjacent (i, i+1) pairs are compared-and-swapped in parallel. After n phases the array is sorted, giving O(n) parallel steps with n/2 comparators each.

19. Parallel shear sort

On a √n × √n mesh, it alternates sorting all rows (snake order) and all columns. After O(log n) such round-trips the mesh is fully sorted in row-major snake order, for total time O(√n · log n).

20. Parallel broadcast / enumeration sort

Enumeration (rank) sort computes, for each element, how many others are smaller by comparing all pairs in parallel; that count is the element's final position. The values are then broadcast/scattered into their ranked slots, sorting in O(log n) depth with O(n2) work.

21. Parallel vs sequential quicksort

(see Part 4(n)) Same O(n log n) work, but concurrent quicksort sorts partitions on separate tasks for ~O(log n) depth and 2–8× speedup, with a sequential cutoff for small arrays.

22. GPU computing; CPU vs GPU

GPUs run thousands of lightweight threads in SIMD groups for massive data parallelism, ideal for regular, arithmetic-heavy workloads. CPUs have few powerful cores with large caches and branch prediction, optimized for latency and complex control flow, whereas GPUs optimize throughput.

23. Communication overhead in distributed systems

Communication overhead is the time spent sending/receiving messages (latency + bandwidth) and synchronizing, rather than computing. It grows with the number of nodes and message frequency and can dominate runtime, so algorithms aim to minimize and overlap communication with computation.

24. Concurrent queue design

A concurrent queue must serialize concurrent enqueue/dequeue operations: a lock-based design uses a mutex (or separate head/tail locks) but can contend, while a lock-free design uses compare-and-swap. Lock-free queues must guard against the ABA problem (a pointer reused between reads), typically with tagged pointers or hazard pointers.

25. Parallel complexity of a reduction/sum

A tree-based reduction combines pairs at each level, so it finishes in O(log n) depth while performing O(n) total additions. This is work-optimal with logarithmic span.

26. Parallel search in a sorted array

With p processors, p-ary search picks p splitters that divide the range into p+1 parts, compares the target against all p in parallel, and recurses into the one sub-range that may contain it. This reduces the depth to O(log n / log p) probes.

27. Parallel graph traversal

Level-synchronous parallel BFS processes one frontier at a time, expanding all its vertices' neighbors in parallel before moving to the next level. DFS is hard to parallelize because its strict depth-first order is inherently sequential.

28. OpenMP vs MPI

OpenMP targets shared-memory machines, parallelizing loops/regions with compiler pragmas over threads in one address space. MPI targets distributed memory, with separate processes that cooperate by explicit message passing (send/recv, collectives).

29. Pseudocode for parallel matrix addition

Every output element is an independent element-wise sum, so all (i, j) can be computed at once.

PARALLEL_MATRIX_ADD(A, B, n):
    parallel for i in 0..n-1:
        parallel for j in 0..n-1:
            C[i][j] = A[i][j] + B[i][j]
    return C
Work O(n2), depth O(1).

30. Work stealing in task scheduling

Each worker keeps its own deque of tasks, pushing/popping from one end; when a worker runs out it steals a task from the opposite end of a busy worker's deque. This balances load dynamically with low contention and is the basis of fork-join schedulers.

31. Consistency models

Consistency models define what ordering of memory operations threads may observe. Sequential consistency requires a single global order matching each thread's program order; causal consistency only orders causally related operations; eventual consistency allows temporary divergence that converges once updates stop.

32. Why linear speedup is hard

Linear speedup is rarely achieved because the sequential fraction caps gains (Amdahl), and real systems add parallelization overhead, inter-processor communication, lock/resource contention, and load imbalance. Together these losses make S grow sub-linearly and eventually plateau.
